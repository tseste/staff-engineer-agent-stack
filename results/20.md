# Bounded remediation proposal

Assumptions: uploads can be disabled independently, and v5 can coexist with v3 through an isolated dependency or service. Other callers require a trust-boundary check. These are proposed actions, not completed work.

**Today:** disable the upload endpoint before parsing, including alternate routes and queued processing. Verify requests cannot reach v3 while the application owner prepares the fix.

Add an upload parser module pinned to a v5 release confirmed to fix the CVE. Commit dependency and lockfile changes together. Review both major-version migrations, runtime requirements, parser defaults, result shapes, and errors. Do not deploy v4 as remediation.

Route uploads exclusively through this module. Translate documented v5 invalid-input errors into the existing application error contract, preserving client responses and logging. Propagate unexpected failures to the server-error handler; never classify every exception as bad XML or fall back to v3. Keep v5 types inside the module. Leave the other 29 callers unchanged only after confirming they cannot receive attacker-controlled input, including stored uploads and background jobs. Otherwise disable those paths too.

**Reopening gates:** the application owner and security engineer verify the dependency graph and production artifact; run the advisory’s regression case in isolation; test valid XML output, malformed XML responses, unexpected exceptions, and upload-to-worker flows. Confirm rejected uploads cause no downstream writes or vulnerable-parser invocation. Compare representative fixtures with prior behavior; run the build and relevant integration suite.

Validate in staging with production uploads disabled. Reopen only onto the verified release; any canary keeps remaining upload traffic disabled. Monitor errors, latency, and resource use. Rollback disables uploads before restoring prior code.

**Follow-up:** assign the application owner a proposed two-business-day deadline to migrate all callers, remove v3 and vulnerable duplicates, repeat scanning and regression tests, and record deployed-version evidence. Containment does not close dependency removal.

## Skill guidance and limitations

Applied dependency-tree analysis, compatibility review, bounded staged upgrades, breaking-change handling, lockfile discipline, integration testing, and rollback planning. Adapted the skill’s one-major-at-a-time suggestion because only v5 fixes the vulnerability. The rollback preserves containment instead of reopening vulnerable processing. No repository, package identity, advisory, deployment controls, or test results were provided; exact error mappings, coexistence feasibility, and exploit-regression expectations must be established during implementation. If isolation cannot be verified today, keep uploads disabled pending a validated broader upgrade.
