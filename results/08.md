# Proposed release: ordered two-step approvals

**Problem and assumptions.** Assume the customer's immediate need is a manager approval followed by finance approval; today the second decision happens outside the product. This story is hypothetical, not validated. Assume existing identity, permissions, and approval screens can be reused. The release makes both decisions visible and enforceable.

**Appetite.** Maximum three weeks with two dedicated engineers, including investigation, verification, and release. This is a spending limit, not an estimate or approved commitment. Ship earlier if complete.

**Solution.** One configuration per workspace: one or two named, ordered approvers, selected from eligible members.

`Settings → select approvers → save → submit request → approver 1 → approver 2, if configured → approved`

Either approver may reject, ending the request. Request detail shows current owner, status, and a read-only chronological history of submission, decisions, and cancellation, with actor and timestamp. Configuration changes affect new submissions only; each submission stores its approver snapshot.

**Rabbit holes settled.** Keep existing submissions on their existing path. Only the active approver can decide; preserve existing eligibility and self-approval restrictions. Persist each decision, history event, and state transition atomically; retries must not duplicate decisions. No in-flight reassignment: if an approver becomes unavailable, an authorized administrator cancels with a recorded reason and the requester submits again. Preserve cancelled history.

**Exclusions.** No arbitrary graphs, parallel branches, conditional rules, quorum voting, delegation, multiple templates, or mobile configuration editing: each expands execution or UI complexity beyond this appetite. No historical audit backfill, exports, or compliance certification. New requests receive basic decision history only.

**Build and breaker.** Both engineers own an integrated slice: configure, submit, decide twice, inspect history. Target demonstration in week one, tackling authorization and atomic transitions first. Then discover scopes and track unknowns; week two completes behavior, week three covers verification and rollout. Verify rejection, duplicate/concurrent actions, unauthorized decisions, unavailable approvers, snapshot changes, and legacy behavior. Cut polish first; retain permissions and history integrity. If essentials remain unresolved at the deadline, keep the existing product and reshape; no automatic extension.

**Guidance used and limitations.** Applied the five-part pitch, fixed appetite, breadboard flow, explicit rabbit-hole decisions, integrated-first delivery, discovered scopes, and circuit breaker from the shaping, betting, building, and anti-pattern references. The maximum prevents appetite becoming a target. This is a bounded engineering proposal, not implemented or tested work; no repository or customer validation was available. Excluded requests can return as evidence-backed proposals rather than promised follow-ups.
