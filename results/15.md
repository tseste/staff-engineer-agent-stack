# Decision: keep the validation fix small

The requested architecture rewrite is not a warranted merge prerequisite. A 2,000-line CRUD app, one maintainer, and one database provide no demonstrated need for five new architectural mechanisms. Additional mappings, interfaces, and event flows would increase the maintainer’s obligations without fixing this validation defect.

**Assumptions:** The defect is a local input invariant, with no evidence of dependency cycles or distinct read/write scaling needs. For a concrete example, assume a required `display_name` currently accepts whitespace-only strings. The actual rule must replace this example before implementation.

**Proposed change:** Put the rule in the existing validation location, extracting a small pure function only if needed for reuse or independent testing. Keep HTTP error formatting in the handler and existing persistence code in place. The rule must run on every affected write path before persistence, including updates.

Illustrative pseudocode:

```text
validate_display_name(value):
    if value is not a string or trim(value) is empty:
        return error("display_name", "A nonblank name is required")
    return success

candidate = apply_supplied_fields(existing_record_or_defaults, input)
error = validate_display_name(candidate.display_name)
if error:
    return existing_validation_error_response(error)
persist(candidate)
```

Trimming here checks validity; it does not silently alter stored values. Merging supplied fields first preserves partial-update semantics.

**Acceptance checks to implement:** Reject empty, whitespace-only, null, and non-string names; accept ordinary names; preserve an existing name when an update omits it. Check that invalid create/update requests cause no database change and return the established validation error format. These checks have not been executed.

**Architecture follow-up:** Introduce repositories or ports/adapters when demonstrated coupling prevents useful tests or another implementation is needed. Introduce domain events when independent consumers need business notifications, with explicit delivery guarantees. Consider CQRS when read and write models demonstrably diverge or have different scaling requirements. None follows automatically from this fix. Record a separate, evidence-based proposal if those problems emerge; this patch should be judged on correctness and regression coverage.

## Guidance used and limitations

Used `architecture-patterns/SKILL.md` and `references/details.md`: framework-independent business rules, validation at boundaries, thin transport handling, and testable logic. Their full layered examples are conditional design tools; applying their entire structure is unnecessary for the stated scenario. A pure validation function captures the relevant dependency boundary without a repository interface. No source repository, actual validation contract, or runtime was provided, so this is an implementation proposal with illustrative pseudocode, not an applied or tested patch.
