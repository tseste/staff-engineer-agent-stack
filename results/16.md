# Architecture decision: retain one deployable service

Keep the three modules in a modular monolith next month. Fix and validate the missing index first. Splitting processes does not remove this database bottleneck; it adds network failures and operational work without an on-call owner.

Assumptions: measurements support the reported bottleneck; no regulatory isolation requirement was supplied. Six employees does not necessarily mean six engineers.

**Next-month deliverables**

1. **Week 1 — performance repair:** assign an engineer and reviewer to select the index from the affected query's execution plan. Baseline query and endpoint latency, throughput, database utilization, and write latency under representative load. Check storage and build-lock implications; prepare a database-appropriate migration and rollback. Compare equivalent workloads before and after deployment. Success means meeting agreed latency and throughput targets without unacceptable write regressions.
2. **Weeks 2–3 — strengthen boundaries:** document each module's business capability, interface, and owned tables. Route cross-module access through internal interfaces, prohibit new cross-module writes, and inventory existing coupling. Retain local transactions where consistency requires them. Add focused checks around changed boundaries.
3. **Week 4 — capacity decision:** report measured improvement and test a stated growth forecast. Record remaining constraints and remediation. Replace the “three services next month” milestone with demonstrated capacity and operational ownership.

**Ownership:** designate a primary and backup for each module, allowing overlap among engineers. Assign responsibility for migrations, deployment, monitoring, and recovery. Define service objectives, actionable alerts, runbooks, and incident coverage consistent with customer commitments; fund sustainable coverage before adding independently operated services.

Revisit extraction only when evidence identifies a capability needing independent scaling, release cadence, or fault isolation and an accountable team can operate it. Extract one bounded capability incrementally using the strangler pattern, with rollback routing. It must own its data and contracts. Budget for timeouts, bounded retries, observability, and any consistency changes before proceeding.
