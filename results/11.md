# ADR-001: Use the existing PostgreSQL job table for asynchronous email

**Status:** Proposed  
**Date:** 2026-10-18

## Context

A three-engineer service needs 20 email jobs/minute. PostgreSQL has spare capacity. Engineering time, reliable delivery attempts, and operating cost drive this decision.

**Assumptions:** Emails can normally wait 60 seconds before dispatch; strict ordering is unnecessary; at-least-once processing is acceptable with duplicate mitigation.

## Decision and alternatives

Use the existing PostgreSQL job table with a background worker.

- **PostgreSQL:** Reuses current infrastructure and permits atomic enqueue alongside application writes. It adds database load and requires us to implement queue behavior.
- **Hosted queue ($150/month):** Reduces queue infrastructure operations and separates queue capacity from the database, but adds recurring cost and another integration. Workers and delivery error handling remain necessary.
- **Self-managed Kafka:** Supports durable event streams and replay, but operating brokers and consumers adds disproportionate work for this team and workload.

## Implementation and consequences

Enqueue transactionally with the triggering application change. Workers claim small batches using `FOR UPDATE SKIP LOCKED`, persist expiring leases, and commit before calling the email provider. Recover expired leases; retry transient failures with bounded exponential backoff and jitter. Retain exhausted jobs for inspection and explicit retry.

Use stable job identifiers and provider idempotency keys where supported. A crash after sending but before recording success can otherwise produce duplicate emails; database transactions cannot guarantee exactly-once external delivery.

This avoids another queue subscription but couples email availability to PostgreSQL and leaves queue maintenance with the team. Index ready jobs, limit worker connections, purge completed jobs on a retention schedule, and monitor oldest pending job age, failures, and database contention.

## Revisit triggers

Reassess if pending-job age exceeds 60 seconds for 15 minutes under healthy provider conditions; queue activity repeatedly harms application latency; sustained volume exceeds 200 jobs/minute; or independent availability, fan-out, or replay becomes required. These are review thresholds, not demonstrated capacity limits. Record a replacement decision in a superseding ADR.
