# Runbook: replay payment jobs safely

For operators recovering failed jobs. Replaying with a new idempotency key can duplicate payments.

**Assumptions:** the example uses job creation time and UTC intervals with an inclusive start and exclusive end. Confirm the actual timestamp field, timezone, and boundary semantics before use. CLI syntax and replay capabilities are unknown; this draft is not executable.

## Outline

1. Purpose, eligibility, access, and payment duplication warning.
2. Select environment, tenant, and dates; inspect candidates.
3. Preserve payment idempotency keys; apply checks below.
4. Execute; capture invocation, run identifier, and progress.
5. Reconcile payments; define completion criteria.
6. Handle partial completion, uncertain outcomes, and duplicates; record handoff evidence.

Link the existing CLI reference for flag definitions. Add supported versions, exit statuses, and cancellation behavior before publication.

## Critical section: verify scope and payment identity

1. Record the target environment, explicit tenant identifier, start, and end. Never rely on tenant or date defaults. Require start before end.
2. Inspect candidates using a supported read-only mechanism. Confirm every job belongs to that tenant and interval; record identifiers and count. Stop for an empty or unexpected selection and investigate.
3. For every payment operation, retrieve its original idempotency key and verify replay preserves it through the payment request. Keep the original payment payload and account context. Never generate replacement keys or reuse one key across unrelated payments. Stop if any key is missing, preservation is uncertain, or the payment system's deduplication retention no longer covers the replay.
4. Compare the execution selection with inspected candidates before launching.

Illustrative preflight record, **not CLI input**:

```yaml
tenant: tenant_acme
created_at: "[2026-10-01T00:00:00Z, 2026-10-02T00:00:00Z)"
job: job_1042
original_key: pay_order_883
replay_key: pay_order_883
```

If the replay key differs, stop. After timeout or partial completion, reconcile payment outcomes before retrying; retain original keys. If duplicates are suspected, stop further submissions and escalate to the payment owner. Cancellation does not reverse completed payments.
