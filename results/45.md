Assumptions: Kubernetes pods share a database; isolated staging approximates production; a previous image is retained. This is a proposed design.

Approval alone preserves both failures: tests discover defects after exposure, and old pods encounter a missing column. Remove the drop from this release.

Required dependency graph:

```text
main push → build → checks → staging migration/deploy
          → staging integration/compatibility tests → approval
          → production additive migration → rolling deploy → verification
```

1. **Build/checks:** Build once; record commit, immutable image digest, and migration checksums. Require unit/security checks. Reject destructive migrations in ordinary releases. Failed, skipped, or timed-out gates block production; approval cannot override them.
2. **Staging:** Migrate representative, sanitized data. Test the previous image against the expanded schema, mixed old/new versions, integration/E2E behavior, and application rollback. Promote the tested digest without rebuilding. Bind approval to that digest and evidence; changes invalidate approval.
3. **Production:** Serialize releases and migrations. Run additive migrations through a tracked, single migration job with lock/statement timeouts; failure blocks rollout. Use rolling updates with `maxUnavailable: 0`, `maxSurge: 1`, dependency-aware readiness, and connection draining. Proposed gates: finish within ten minutes; monitor safe synthetic transactions and error/latency SLOs. Missing monitoring, readiness failure, timeout, or SLO breach stops deployment and restores the previous digest. Verify rollback; retain the expanded schema. Production probes supplement staging tests and use isolated records.
4. **Separate contraction:** Deploy code that stops accessing the obsolete column. If replacing it, add the replacement, maintain compatible writes, backfill idempotently, validate completeness, then switch reads. Retain the old column throughout the rollback window. Drop it only after evidence confirms old pods, workers, scheduled jobs, and other consumers across environments are retired and every supported rollback image tolerates its absence. Rehearse the drop and recovery, retain a verified backup, and approve separately. Application rollback cannot recover dropped data; use the rehearsed data-recovery procedure.

Actual SLO thresholds, schema details, backfill strategy, CI syntax, and recovery time must be configured and tested against the real service.
