# Export endpoint remediation

Assumptions: exports contain confidential data; server-maintained memberships and an explicit export permission determine access. Suggested owners are roles, not assigned people.

Threat: authenticated users can substitute account IDs; log readers can replay bearer URLs. Trust boundaries include API, database, storage, downloader, and telemetry.

**P0 — Backend owner: authorize before export access.** Validate the identifier; resolve current membership and export permission for that account from trusted server state. Deny missing permission or unavailable policy. Scope parameterized queries and private export objects to the authorized account. Client identifiers never confer authority. Workers, if present, independently enforce authorization. Return consistent denials without revealing account existence.

**P0 — Platform/security owners: contain URL exposure.** Stop logging URLs/signatures across application, proxy, tracing, error, and storage telemetry. Allowlist audit fields: actor, account, action, authorization outcome, time, correlation ID, policy version. Restrict historical logs; preserve minimal investigation evidence. Identify outstanding exports and invalidate exposed links through supported revocation or object removal; verify denial. New expiry settings do not invalidate existing links. Investigate exposure without assuming misuse.

**P1 — Backend/platform owners: replace seven-day links.** Prefer authenticated downloads that recheck current permission before streaming private objects. If direct signed downloads remain necessary, propose five-minute maximum expiry, exact-object GET scope, TLS, and private storage. Copied links remain usable until expiry unless revoked; record this residual risk. Define export retention/deletion.

**P2 — Backend owner:** bound export size/concurrency; serialize CSV correctly and neutralize spreadsheet formulas in untrusted text.

Required regressions:

- Authorized users receive only their account’s sentinel rows. Cross-account access, missing export permission, revoked membership, and policy failure deny without export-data reads, object creation, or signing.
- Direct endpoints and applicable workers reject substituted account/object references.
- Private objects reject unsigned access; signed links reject changed objects/methods and expired requests; exposed links fail after containment.
- Success/error telemetry contains no URLs, signatures, or CSV contents, but preserves attributable authorization decisions.
- Authenticated downloads deny after permission revocation; malformed identifiers, CSV formulas, and export-limit violations fail safely.

## Guidance used and limitations

Applied the skill’s threat-modeling, authorization, tenant-isolation, data-handling, secrets-lifecycle, secure-logging, and release-evidence guidance. These establish server-enforced boundaries, explicit bearer-token residual risk, and negative regression criteria. No repository or provider configuration was supplied; no implementation or tests were performed. Release evidence must identify actual owners, revision, deployed configuration, test results, and any time-bounded exception. Storage-specific revocation semantics remain an evidence gap.
