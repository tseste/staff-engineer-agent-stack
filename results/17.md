Decision: keep the existing CRUD application and one database. Separate persisted read models and event sourcing are unjustified for 30 writes/hour, 3 reads/second, daily exports, and a lightly loaded database. The read/write ratio alone does not establish a scaling problem. Event sourcing and CQRS are independent choices; neither is necessary to produce CSV reports.

Assumptions: a relational database is available; reports describe current state at generation time, rather than reconstructing every historical change. Proposed schedule: daily at 00:05 UTC, with each export labeled by its snapshot timestamp. Exact business cutoff requirements remain a design assumption.

Smallest implementation:

1. Keep transactional CRUD writes, including authorization, validation, and database constraints. Read committed changes directly from the same database. Separate mutation functions from read functions where useful; no command bus is needed.
2. Implement one reporting query, optionally encapsulated in an ordinary SQL view. Select explicit columns and a deterministic order. For an illustrative `records` table:

   ```sql
   SELECT id, name, status, updated_at
   FROM records
   ORDER BY id;
   ```

3. Add one scheduled export task to the existing deployment. Execute the query under a database-supported consistent read snapshot, stream rows through a standard CSV writer to a temporary file, and publish the dated file atomically after successful completion. Record snapshot time, row count, and success/failure. Retry failures; if that day's completed artifact already exists, retain it and exit successfully. Provide downloads through existing admin authorization.
4. Validate CSV quoting, empty results, concurrent edits, and interrupted-run recovery. These are proposed checks; none have been run. Inspect the real query plan before adding indexes.

Measure export duration, database contention, and interactive response time. Only demonstrated contention or independently evolving query needs justify considering a materialized view, reporting replica, or CQRS. If historical reconstruction becomes necessary, define the history requirement first; a small audit/history table may suffice. Retained daily CSVs preserve daily snapshots, not intermediate changes.
