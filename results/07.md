# Five-day CSV export execution approach

Use a short delivery plan and an early streaming experiment. Agreed scope and an existing query make memory validation the priority over charter paperwork.

**Assumptions:** three engineers have protected capacity; scope requires 1M-row exports; no mandatory charter policy is known. Five days remains conditional on validation. Proposed authority: manager owns scope/date tradeoffs; engineering lead owns implementation; the existing acceptance owner signs off, or the manager identifies one on day 1.

Keep one shared ticket containing scope, owners, checkpoints, evidence, and the memory risk. Propose it as the charter equivalent. If a full charter is mandatory, populate required fields from that ticket.

**Proposed work allocation and checkpoints:**

- **Day 1:** Engineer A time-boxes a streaming spike to half a day using the existing query, a database cursor or bounded batches, incremental CSV encoding, and response backpressure. B prepares representative fixtures; C checks the integration path and deployment memory budget. A and C review evidence that afternoon.
- **Day 2:** A hardens streaming; B integrates the agreed export entry point; C verifies CSV correctness and failure handling.
- **Day 3:** Integrate end to end and exercise 1M rows, slow consumers, cancellation, and database errors. Fix any buffering or resource leaks.
- **Day 4:** Complete regression checks and acceptance review; resolve defects.
- **Day 5:** Preserve capacity for rework, then use the existing release process and record acceptance and residual ownership.

Before the spike, agree a memory ceiling from deployment headroom and expected concurrency. Record peak memory across increasing row counts: passing requires staying below that ceiling without memory growing proportionally with total rows, plus correct output. A spike alone does not establish release readiness.

A owns the memory risk. Missing or failed evidence on day 1 triggers an immediate manager decision: change implementation and revise the forecast, or explicitly reduce scope. Never silently truncate exports.

Replace separate daily RAG documents with one daily ticket comment: evidence, forecast/risk, next decision. Initial feasibility is **unknown**; unresolved memory risk prevents an unqualified green.

**Skill guidance and limitations:** Applied the smallest-adequate-method rule, method-selection tailoring, adaptive delivery’s bounded learning checkpoint, and control-and-communication’s evidence-based status and immediate escalation. Kept approval, forecast, and acceptance distinct. No repository, deployment limits, performance measurements, accepted assignments, or release approvals were supplied; this is a proposed execution plan, not evidence that delivery is feasible or complete.
